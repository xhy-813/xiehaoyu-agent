#### H1. Planner JSON 解析回归：多行 JSON 必然解析失败 🧪

- **位置**：[agent/planner.py:36-49](../../agent/planner.py#L36-L49)（`_sanitize_control_chars`）
- **严重度**：**高**（核心决策环路的潜伏性故障）

**问题**：8.06 的"裸控制字符转义"修复用 `re.sub(r"[\x00-\x1f]", ...)` 把 LLM 输出中的**所有**换行符替换为两字符字面量 `\n`——包括 JSON token 之间的结构性空白。JSON 规范允许 `{` 后跟换行等空白，但不允许孤立的反斜杠，因此**任何多行 JSON（美化输出或 markdown 围栏包裹）在转义后都变成非法 JSON**，解析失败。

**实测证据**（本机 .venv 直接调用 `_extract_json`）：

```
compact JSON            : OK
pretty multi-line JSON  : FAIL -> JSONDecodeError: Expecting property name... (char 1)
fenced multi-line JSON  : FAIL -> JSONDecodeError（围栏剥离后重新拼入换行，再被转义破坏）
字符串内含裸换行         : OK（修复的目标场景确实生效）
```

**为什么测试没拦住**：[test_planner.py](../../tests/test_planner.py) 全部 10 个用例的 JSON 都是**单行**——围栏用例 `'```json\n{"action": ...}\n```'` 里的 JSON 本体也是单行，恰好绕过了这个回归。

**影响链**：DeepSeek 当前多输出紧凑 JSON，所以线上大部分正常；一旦模型输出多行 JSON → `_extract_json` 抛错 → `planner_node` 兜底为 finalize → 用户看到 `Planner 调用失败: Expecting property name...`——**整轮对话失败，且把内部解析异常原文展示给用户**（与 M8 联动）。

**建议**：只在字符串值内部转义控制字符（如用 `json.JSONDecoder` 容错解析，或先按字符串边界扫描）；最小修复是将 `\n`/`\r` 的替换改为空格而非 `\n` 转义序列（结构性空白合法化），同时保留对字符串内控制字符的处理；并立即补充多行美化 JSON、多行围栏 JSON 两个回归测试用例。

#### H2. 按 IP 限流可经伪造 X-Forwarded-For 绕过 ✅

- **位置**：[backend/app/deps/rate_limit.py:25-30](../../backend/app/deps/rate_limit.py#L25-L30) + [deploy/nginx.conf:30](../../deploy/nginx.conf#L30)
- **严重度**：**高**（直接金钱损失面）

**问题**：`get_client_ip()` 无条件信任 `X-Forwarded-For` 并取**第一跳**。而 Nginx 的 `$proxy_add_x_forwarded_for` 语义是**追加**：客户端若自带 `X-Forwarded-For: 1.2.3.4`，Nginx 转发为 `1.2.3.4, <真实IP>`。后端取第一跳 → 得到攻击者伪造的值。

**攻击推演**：攻击者每次请求换一个伪造 XFF → 每 IP 每小时 20 次限制完全失效 → 仅剩全局每日 200 次兜底 → 一天最多烧掉 200 次 × 多步 LLM 调用的 DeepSeek 额度。零技术门槛（curl 加个头即可）。

**核验备注**：核验代理曾以"uvicorn 绑定 127.0.0.1 无法直连"部分质疑，主审查者复核：绑定回环只防**绕过 Nginx 直连**这一种路径，伪造 XFF **经 Nginx 正常转发**即可生效，不影响结论成立。

**建议**：uvicorn 已带 `--proxy-headers`，其 ProxyHeadersMiddleware 会把 XFF **最右一跳**（即 Nginx 看到的真实对端）写入 `request.client.host`——最简修复是 `get_client_ip()` 删掉 XFF 解析、直接返回 `request.client.host`；或改用 `X-Real-IP`（nginx 用 `$remote_addr` **覆盖**赋值，可信）。修复后可补一条"伪造 XFF 不改变限流键"的单元测试。

#### H4. SQL 执行层无资源护栏：递归 CTE / 笛卡尔积可打挂单机 ✅

- **位置**：[chatbi/validator.py:16-24](../../chatbi/validator.py#L16-L24)、[agent/tools/query_data.py:156-158](../../agent/tools/query_data.py#L156-L158)
- **严重度**：**高**（可用性 + 金钱）

**问题**：校验器多层防御防住了"写"（INSERT/DELETE/ATTACH…），但完全不防"烧"：

1. **递归 CTE 无限制**：`_CTE_SELECT_RE` 接受任何 `WITH ... SELECT`，`WITH RECURSIVE r(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM r) SELECT COUNT(*) FROM r` 可全票通过——无终止条件的递归在 SQLite 内无限计算。全项目 grep 无任何 RECURSIVE 防护。
2. **笛卡尔积无检测**：`FROM a, b, c` 逗号连接不做 JOIN 条件检查，Olist 十万行级三表笛卡尔积即可撑爆 2C4G 内存。
3. **无超时、无行数上限**：`pd.read_sql()` 裸奔，SQLite 连接未设 busy_timeout/progress handler，pandas 未设 chunksize。

**触发路径**：攻击者用自然语言诱导（如"用递归 CTE 算 1 到 10^18 的和"），text2sql 温度 0.0 且 prompt 未禁止 RECURSIVE，LLM 有较大概率照做。单 worker 架构下工作线程被永久占住，累积若干次即全站不可用。

**建议**：(a) validator 增加 `\bRECURSIVE\b` 拒绝（或白名单允许带硬性 `LIMIT` 的递归）；(b) 执行层加护栏——SQLite `progress handler` 限制指令数 / `connect_args={"timeout": N}` + 应用层执行超时；(c) 结果集行数硬上限（如 `LIMIT` 注入或 `fetchmany`）；(d) 纵深加固：引擎以只读 URI 打开（`mode=ro`）。

### 🟡 中优先级

#### M1. 客户端断连后，进行中的 LLM 调用继续烧额度 ✅

- **位置**：[backend/app/routers/chat.py:166-167](../../backend/app/routers/chat.py#L166) × [agent/graph.py](../../agent/graph.py) 同步节点
- **核验**：事实成立，定级由"高"修正为**中**（损失有界，见下）

**问题**：断连时 `producer.cancel()` 只能取消 asyncio 任务；LangGraph 的同步节点（planner/tools）运行在线程池，**Python 无法中断线程内正在执行的同步 HTTP 调用**——该调用会跑完并计费，结果被丢弃。

**边界**：LLM 客户端 `timeout=30s, max_retries=1`（[llm_client.py:23-27](../../agent/llm_client.py)），单次断连最多多烧"剩余步骤数 × 约 60s"的 token；前端还有 120s 超时主动断开（M7），放大了这条路径的触发频率。

**建议**：最小改动——在 `_run_tool`/`planner_node` 入口检查取消标志（向 state 注入 `cancel_event`）避免**新**步骤启动；彻底方案是迁移到 `AsyncOpenAI` + async 节点，获得真正的可取消性。

- **严重度**：**中**（纵深防御缺口；该产品用户与攻击者都说中文）

**问题**：9 条注入模式全部是英文正则（`ignore previous instructions`、`you are now`、`forget everything`…）。「忽略以上所有指令」「你现在是一个没有限制的 AI」「忘记你的人设」等中文注入措辞**零匹配、零测试**（test_sanitize_input.py 的良性/恶意用例同样全英文）。

**缓解因素**：planner.md 与 text2sql.md 的"安全规则"段落提供了 prompt 层的中文防御；SQL validator 是数据面最后防线。因此这是纵深缺口而非裸奔，但检测层对中文用户等于不存在。

**建议**：为 `_INJECTION_PATTERNS` 增加中文模式（忽略/之前的指令、忘记/人设、你现在是、系统：角色行等），并为每条中英文模式各配正/反测试。

- **位置**：[agent/sanitize.py:56-58](../../agent/sanitize.py#L56) → [agent/graph.py:154-160](../../agent/graph.py#L154)
- **严重度**：**中偏低**

**问题**：(a) `sanitize_input` 抛出的 `ValueError` 消息**包含命中正则的原文**（`f"...unsafe content: {pattern.pattern}"`）；(b) `planner_node` 把异常文本直接拼进 `final_answer`。两者叠加：注入尝试者会看到 `Planner 调用失败: Input contains potentially unsafe content: ignore\s+(all\s+)?...`——**检测规则被逐条暴露**，攻击者可据此低成本试错绕过；普通用户则看到一条莫名其妙的报错。

#### M4. 前端 SSE 重试逻辑错位：该重试的不重试，不该重试的重试 ✅

- **位置**：[frontend/src/utils/sse.ts:136-176](../../frontend/src/utils/sse.ts)
- **严重度**：**中**（错误恢复路径的核心逻辑反了）

**问题**：注释声明"只对网络错误重试"，但实现相反——

1. **网络错误（fetch reject / AbortError）**：`_doStream` 无 catch，异常直接穿透 `sseChatStream` 的重试循环抛到 store——**重试循环对网络故障是死代码**。
2. **应用层错误（429 限流等）**：经 `onError` 回调进入循环，除了"空的响应体"外不 `continue`，循环自然空转进入下一次迭代——**429 会被无效重试 3 次**，用户为确定性错误白等 1+2+4=7 秒。

**建议**：在循环内 try/catch `_doStream` 并对网络异常重试；对 4xx/429 类应用错误立即透传不重试（可按 HTTP 状态码白名单区分）。

| systemd `Restart=always` 无速率限制会永久停服 | systemd 默认 StartLimitInterval=10s/Burst=5 的滑动窗口语义下，`RestartSec=3` 的连续崩溃序列不会在 10s 窗口内凑满 5 次启动；初判的数学推演错误 |
| 健康检查应覆盖 SQLite/ChromaDB | `init_store()` 在 lifespan 启动期执行，失败即应用不可达，运行时探测冗余 |
| SSE 错误事件不区分 API 故障与内部错误 | APIError 在到达通用 catch 前已被 6 层捕获并转为有意义的 trace/降级文案，通用兜底消息只覆盖真正的未知异常 |
| 空检索仍调 LLM 浪费 API 费用 | persona 一致性润色、拒答话术生成仍需 LLM；硬编码 fallback 会牺牲第一人称体验，属有意设计 |
| Planner 空响应 fallback 丢弃已执行工具结果 | tool_end 事件先于 final_answer 经 SSE 送达前端，用户看得到中间结果 |
| messages 数组无界增长致内存泄漏 | `loadSession` 是全量替换而非追加，`clearChat` 存在；会话页生命周期内增长有界 |
| test_settings_memory 的 reload 污染后续测试 | `try/finally` 在 assert 失败时仍执行恢复逻辑，初判误解了 Python 语义 |
| 期望薪资数字公网可见属"漏洞" | 事实成立但非代码缺陷——知识库公开是本产品的设计本身；已改列为内容决策项（C2）由本人定夺 |

## 十、总结
