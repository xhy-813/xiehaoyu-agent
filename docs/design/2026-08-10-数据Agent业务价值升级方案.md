## 目标

三项改动服务同一个判断标准：**面试官随便问一个数据问题，得到的不是一锤子数字，而是「口径明确的数字 + 业务解读 + 可继续深入的下一步」，且多轮追问不断上下文。**

现状家底（不重复建设）：Text2SQL 四层纵深防御 + 50 题无泄漏基线 96%、全链路异步 SSE、citations 渲染先例（08-09 T4-1）、会话持久化 + 触发式摘要 + history_text 注入链路、prompt 版本头约定。

## T1 追问引导 + 裸查询必带解读

**问题**：explain.md:36 明文把「建议进一步分析」列为反面示例，分析停在一锤子回答；planner.md:36 纯查询链路只出数字不出解读，白白放弃引导面试官走完「查数→出图→解读→下钻」能力链的机会。

**改法**：

1. **prompts/explain.md** v1.2.1 → v1.3.0：删除【反面示例】第 3 条禁令，新增【追问建议】段——输出末尾必须追加固定格式块，2-3 条**具体可执行**的下一步问题（下钻维度 / 对比期间 / 异常验证，必须是 Olist 数据集可回答的，禁止空洞的「建议进一步分析」）：
   ```
   【追问建议】
   1. …
   2. …
   ```
2. **agent/tools/explain_result.py**：返回值 `str` → `ExplainResult` dataclass（`insight: str, followups: list[str]`）。解析末尾【追问建议】块：insight 正文剔除该块；解析失败或无块 → `followups=[]`、insight 保留原文（优雅降级）。
3. **agent/graph.py**：`_run_tool` explain 分支（:132-134）`artifact = {"insight": r.insight, "followups": r.followups}`；`_summarize` explain 分支（:88-89）改返回 `r.insight[:800]`——**planner 上下文不含追问块，finalize answer 不复述追问**，避免与前端 chips 重复展示。
4. **prompts/planner.md**（并入 v1.4.0，见 T2）：工具选择「纯数据查询（统计/排名/趋势）→ query_data」改为「→ query_data → explain_result → finalize」（裸查询必带解读；explain 输入仅 20 行预览，token 成本可控）。
5. **前端**（照 citations 先例：SSE artifact → trace → 提取渲染）：
   - `utils/sse.ts` `Artifact` 加 `followups?: string[]`；`utils/artifact.ts` 新增 `findFollowups(trace)`（倒序找最后一个含非空 followups 的 artifact，照 `findCitationArtifact`）
   - `ChatMessage.vue` 的 `InlineResult`（:92）之后渲染追问 chips，条件 `assistant && !isStreaming && followups.length`；点击调 `chat.sendMessage(q)`（程序化发送先例：ChatView.vue:127-130 的 `ask()`），流式中禁用；样式参照 WelcomeScreen 的 `ws-chip`，CSS 变量适配双主题
   - 回放会话因 trace 落库含 `artifact.followups`，chips 免费可用

**验收**：每条数据回答自带解读 + 末尾 2-3 个可点击追问 chips，点击即发送；追问具体（带维度/期间/指标），非空话；回放会话 chips 仍渲染。

## T2 指标口径注册表 + 不确定反问

**问题**：GMV/复购率/客单价无独立定义，口径散落在 text2sql.md 的 SQL 技巧条文里（:26、:36、:38-47），同一指标两次提问可能出不同数字；且 96% 基线有水分——评测题干内嵌了口径定义（eval_text2sql.py:338、451、467、481）。

**改法**：

1. **新增 chatbi/metrics.py**（纯 Python 照 `few_shots.py` 先例，不引入 yaml——pyyaml 非直接依赖）：
   - `METRICS: list[dict]`，字段 `name` / `aliases` / `definition`（业务口径）/ `sql_hint`（SQL 写法要点）/ `unit`
   - 初始 12 指标：GMV（SUM(price)，delivered 口径，BRL）、订单量（COUNT DISTINCT order_id）、客单价（GMV/订单量）、复购率（≥2 次购买的 customer_unique_id 占比）、新客占比、平均评分、差评率（≤2 分占比）、准时交付率、平均交付时长、运费占比、平均分期数（credit_card 口径）、品类集中度 CR5
   - **字段级语义**（吸收 DataAgent 语义模型层实践：同义词与枚举值解释是最高 ROI 配置）：`FIELD_SEMANTICS` 段为枚举字段写取值解释（`order_status` 各取值业务含义及其与 GMV delivered 口径的包含关系、`payment_type` 各取值），为易混字段写业务名称与同义词（`price` = 商品售价 ≠ `payment_value` 实付金额）。分层纪律：字段映射与枚举解释放字段层，计算口径只放指标层，互不越界
   - `format_metrics()`（完整版，text2sql 用）+ `format_metrics_brief()`（紧凑版：名称+别名+一句话口径，planner 用）
   - 约束：渲染文本不含 `{}` 花括号（text2sql.md 走 `str.format`）
2. **prompts/text2sql.md** v1.5.1 → v1.6.0：
   - 新增【业务指标口径】段 + `{metrics}` 占位（插在 :36 之后、【COUNT 语义规则】之前）；口径语义条文（消费金额按 price、customer_unique_id 去重、COUNT DISTINCT 语义）**迁入注册表**，本文件只留 SQL 写法规则——口径单一事实源是注册表，消除双写漂移
   - 写入两条高频坑规则（吸收 DataAgent 语义审计清单，零运行时成本）：DATETIME 范围过滤用半开区间（`>= '2018-01-01' AND < '2019-01-01'`），避免 `BETWEEN ... AND '2018-12-31'` 丢失结束日当日数据；多对多 JOIN 后聚合前先检查扇出（orders × order_items 后直接 SUM 订单级字段会重复计数）
3. **agent/tools/query_data.py** `_build_prompt`（:89-97）：注入 `metrics=format_metrics()`。
4. **prompts/planner.md** v1.3.0 → v1.4.0（与 T1 第 4 条、T3 第 4 条合并升版一次）：
   - 新增【业务指标口径】节 + `{metrics_brief}` 占位
   - 新增规则：命中注册表 → 直接查；涉及**注册表外模糊指标词**（"效率/质量/表现/好不好"等无公认口径）→ 不猜，finalize 反问；反问话术标准（吸收 DataAgent 澄清节点设计）：**最小具体、列出当前可选口径**（2-3 个候选让用户挑一个即可回答）
5. **agent/planner.py** `_load_planner_system`：注入紧凑清单。**注意**：planner.md 含 JSON 示例花括号，禁止 `str.format`，用 `content.replace("{metrics_brief}", ...)`。
6. **评测**：tests/eval_text2sql.py 新增 6 道口径题（`level="metric"`，只给指标名不给口径，如「复购率是多少」「客单价最高的三个品类」），与 few-shot 零重叠（沿用 808 H3 纪律）；报告按 level 分层，支持 `--level metric` 单跑。

**验收**：6 道口径题 ≥5/6；原 50 题基线不回退（波动 >2% 需说明）；同一指标两种问法（「复购率」「购买 2 次以上的客户占比」）出同一数字；「客户质量怎么样」类模糊问题触发反问而非硬猜；改 metrics.py 一处定义后两种问法结果同步变化（现场可演示）。

## T3 分析上下文连续性

**问题**：会话记忆只服务「聊天连贯」而非「分析连续」——上轮 SQL/口径轮间丢失（planner.py:173-178 history_text 仅文本注入；graph.py:378-383 每轮 initial_state 全新），「把刚才的结果按州拆分」必须从头重查。

**改法**：

1. **prompts/summary.md** v1.0.0 → v1.1.0：保留项增加「已确认的数据口径与关键结论（含具体数字）」。
2. **backend/app/services/session_store.py**：新增 `get_last_analysis(session_id) -> dict | None`——查最后一条 `role='assistant' AND artifacts_json IS NOT NULL` 的消息并解析 JSON（不改表结构）。
3. **backend/app/routers/chat.py**（:210-213 history_text 拼装处）：追加 `[上轮分析]` 块——从 trace 提取最后一个 query_data 的 `artifact.sql`、explain 的 `artifact.insight`（截断 ~300 字）、对应用户问题；无分析痕迹则不追加。追加逻辑放 chat.py，`build_history_text` 纯函数不侵入。
   ```
   [上轮分析]
   问题: …
   SQL: …
   结论: …
   ```
4. **prompts/planner.md**【会话记忆】节（:63-68，并入 v1.4.0）：说明 `[上轮分析]` 块含义；改写类追问（"按州拆分""换成 2017 年"）在 `args.question` 末尾附「参考上轮 SQL：…」；追问中的相对时间（"上个月""去年"）换算为绝对日期后传入。
5. **prompts/text2sql.md**（并入 v1.6.0）：新增一条——问题附「参考上轮 SQL」时在其基础上改写而非从零编写。

**验收**：「把刚才那个结果按州拆分」正确产出（执行轨迹可见 SQL 在上轮基础上改写）；「换成 2017 年再看」正确替换时间过滤；摘要中包含口径条目。

## 风险与对策

| 风险 | 对策 |
| ---- | ---- |
| 追问块解析失败或 LLM 不按格式输出 | 解析失败降级 `followups=[]`、insight 保留原文；前端无 chips 不影响现有渲染 |
| planner 反问误判（该查的问题反问了） | 反问规则限定「注册表外**且**无公认口径的模糊词」；命中注册表一律直接查；6 道口径题回归覆盖 |
| 裸查询强制 explain 增加 token 成本与延迟 | explain 输入仅 20 行预览；planner 对「只要数字」的显式指令仍可跳过（prompt 写明例外） |
| `[上轮分析]` 块膨胀 planner 上下文 | SQL 全量（一般 <500 字）+ insight 截断 300 字；仅取最近一轮，不累积 |
| 注册表口径与 text2sql.md 双写漂移 | 口径语义只存 metrics.py（单一事实源），text2sql.md 只留 SQL 写法规则；审查时专项检查 |
