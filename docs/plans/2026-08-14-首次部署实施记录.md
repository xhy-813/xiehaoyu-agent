## 问题记录（4 + 1 个，均已解决；3 项需仓库级跟进）

### 问题 1：deploy.sh 在 git 中无执行位

- **现象**：首次 `sudo nohup ./deploy/deploy.sh` 报 `Permission denied`；服务器上 `ls -l` 显示 `-rw-r--r--`
- **原因**：git 树中文件模式为 100644。本地 Git Bash 显示的 `rwxr-xr-x` 是 Windows 下 MSYS 对 .sh 的假象，不代表 git 树模式
- **处置**：服务器上 `chmod +x`（脚本头部注释本就写明用法含 `chmod +x`）
- **仓库级建议**：本地执行 `git update-index --chmod=+x deploy/deploy.sh` 并提交，根治

### 问题 2：Node v20.17.0 低于 vite 8 的引擎要求

- **现象**：npm install 时大量 `EBADENGINE` 警告（`vite@8.1.5` 要求 `^20.19.0 || >=22.12.0`）
- **处置**：升级到 npmmirror 上 v22 最新 **v22.20.0**（npm 10.9.3）。计划文件中的 Node 版本以本文档为准
- **备注**：升级时直接覆盖解压导致新旧 npm 文件混杂（`Class extends value undefined`），**先 `rm -rf /usr/local/lib/node_modules` 再解压**后正常。Node 升级务必先清旧目录

### 问题 3：Windows 生成的 package-lock.json 在 Linux 丢 rolldown 原生绑定（npm/cli#4828）

- **现象**：`vite build` 崩溃：`Cannot find module '@rolldown/binding-linux-x64-gnu'`；带 lock 安装仅 122 包
- **原因**：lock 由 Windows 端生成，npm 的已知跨平台 bug 会跳过 Linux 平台可选依赖
- **处置**：服务器端 `rm -rf node_modules package-lock.json` 后全新安装（124 包，含 `binding-linux-x64-gnu`），build 通过
- **遗留影响**：服务器上的 lock 是 Linux 重新生成的，与 git 仓版本不一致——未来服务器 `git pull` 若遇 lock 更新会报本地修改。属一次性部署环境差异，不影响运行
- **仓库级建议（待用户决策）**：a) 本地用 npm 11 重新生成 lock 提交（不一定根治 4828）；b) 从仓库移除 frontend/package-lock.json（放弃构建可复现性换跨平台省心）；c) 维持现状，部署文档补一条「服务器端删 lock 重装」。推荐 c 起步，等 vite/rolldown 稳定后再评估

### 问题 4：systemd mount namespace 崩溃循环（226/NAMESPACE）

- **现象**：deploy.sh 报「部署完成」但后端反复重启（计数到 68）：`Failed to set up mount namespacing: /srv/xiehaoyu-agent/chatbi/data: No such file or directory`
- **原因**：unit 的 `ReadWritePaths` 含 `chatbi/data/`，但该目录因 `chatbi/data/*.db` 被 gitignore 而不随 clone 存在；systemd 对不存在的 ReadWritePaths 直接起不来
- **处置**：`mkdir -p chatbi/data` 后重启即 `active`（该目录本就是 Step 4 的上传目标）
- **教训**：**deploy.sh 输出「部署完成」≠ 服务可用**——`Type=simple` 下 `systemctl restart` 不等待就绪。验收必须以 `is-active` + health 端点为准（deploy.sh 可考虑加一行 health 检查作为收尾）
- **仓库级建议（待用户决策）**：a) 仓库加 `chatbi/data/.gitkeep` 让目录随 clone 存在（最小改动）；b) unit 删除 `chatbi/data/` 的 ReadWritePaths 条目（olist.db 本来就是 `mode=ro` 只读打开，ProtectSystem=strict 下无需写权限）；c) deploy.sh 的 `install -d` 一步顺带创建该目录。推荐 a 或 c

### 问题 7（外部原因，非系统故障）：DeepSeek 夜间性能抖动导致前端 180s 超时

- **现象**（00:01–00:08 用户实测）：/chat 提问一直提示「响应时间较长，请稍后重试」
- **排查**：后端 active；请求正常到达（6 次 chat start）但 **LLM 调用全部卡在 60s 超时 + openai 客户端重试**，日志无一条 llm_tokens 完成记录；单轮 Agent 需 3-4 次 LLM 调用，累计超过前端 SSE 180s 超时（chat.ts:187 的提示文案正是该分支，属设计内行为）
- **验证**：00:10 从服务器实测 DeepSeek 最小调用 1.16s；从公网完整复测「2018年订单数」端到端 **6.4s 正常返回**（54011）。证实为 DeepSeek 服务端在该窗口的性能抖动，本系统无故障
- **结论**：无需处置。面试季若再现，先跑一轮 curl 复测——恢复即外部原因；前端 180s 超时 + 友好文案即为兜底设计。排障注意：journalctl `--since "23:45"` 在跨午夜时会解析为未来时间导致查无日志，须用绝对时间戳

### 问题 5（测试侧，非服务器问题）：curl 内联中文 JSON 被 Windows 转码

- **现象**：SSE 验证首次返回 `{"detail":"There was an error parsing the body"}`
- **原因**：本机 Git Bash 调 curl.exe 时内联中文参数被按本地代码页转码，非 UTF-8
- **处置**：请求体写入 UTF-8 文件后 `--data-binary @file` 发送，正常

### 问题 6：HTTP 裸 IP 下 `crypto.randomUUID` 不可用，前端全部 API 调用静默死亡（当晚用户实测发现）

- **现象**：部署当晚用户在 /chat 页无法发消息；后端 active、健康检查正常，且 **Nginx 访问日志中零条该用户的 /api/ 请求**——浏览器根本没发出请求
- **原因**：`crypto.randomUUID()` 仅在**安全上下文**（https 或 localhost）可用；`http://IP` 页面里它是 undefined。本地开发（localhost:5173）永远正常，上线到裸 IP 才暴露。调用链：`getUserId()`（user.ts:7）→ 抛 TypeError → `api()`/`sse.ts` 在 fetch 之前死亡；`chat.ts:122,131` 生成消息 id 也用同一 API（同样会炸）。页面壳正常渲染，所以极具迷惑性
- **处置**：新增 [frontend/src/utils/uuid.ts](../../../frontend/src/utils/uuid.ts)——有 `randomUUID` 就用，没有则用 `crypto.getRandomValues`（不受安全上下文限制）手拼 RFC4122 v4；user.ts 与 chat.ts 三处全部换用。本地构建（vue-tsc + vite）通过 → dist 上传服务器 `mv` 原子切换 → 公网验证新 ChatView 包（894KB）含降级代码 ✓
- **部署方式备注**：本次热修直接上传本地构建的 dist（dist 被 gitignore，服务器源码树未动，无分叉）；**uuid.ts / user.ts / chat.ts 的本地改动尚未提交，待用户提交推送**
- **教训**：localhost ≠ 生产环境。凡涉安全上下文受限 API（`crypto.randomUUID`、`navigator.clipboard` 等），上线前需在 `http://IP` 下实测。clipboard 三处已有 try/catch 兜底（复制失败不阻断），randomUUID 是漏网之鱼
