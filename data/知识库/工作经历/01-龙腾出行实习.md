# 龙腾出行实习 · 数据工程与 AI 赋能

## 关键信息
- 公司：龙腾出行（DragonPass）
- 部门：AI 研发部 / 数据平台组
- 岗位：数据实习生
- 时间：2026 年 04 月 - 至今
- 技术栈：Python、SQL（MySQL）、DataPipeline 框架、FineBI、千问大模型（Qwen / DashScope）、Google Maps API、高德地图 API、Tavily Search API、Git、Docker
- 数据规模：国内外 10 万余条 POI + 行程数据，覆盖上海、北京、广州、成都、深圳、香港、东京等 10+ 城市

## 背景 (Situation)

龙腾出行是做机场 / 高铁贵宾厅和差旅出行服务的公司，AI 研发部在做一个面向用户行程场景的 **POI（Point of Interest）+ 行程知识库**，用来给上层业务（智能推荐、行程规划）提供基础数据。原始数据来自 Google Maps、高德、Tavily 三个外部 API，字段口径不统一、境内外差异大、描述字段普遍缺失，导致下游没法直接用。我作为数据实习生，在 mentor 指导下负责这条 DataPipeline 的开发、清洗、质量监控与 LLM 增强。

## 任务 (Task)

1. 打通 city / poi / itinerary 三条子 Pipeline 的多源采集、清洗、入库全链路
2. 为 10 万+ 条 POI 数据建立**质量基线和监控机制**，避免脏数据流向下游
3. 排查 POI **匹配失败率高**的问题，做归因并输出可落地的兜底策略
4. 梳理 POI / 行程的**多维指标口径**，让迭代有数据依据
5. 用 LLM 补齐 POI 缺失的 `title` / `description` 字段，把描述覆盖率从 0 拉起来

## 行动 (Action)

### 1. 数据管道建设

基于公司内部的 **DataPipeline 框架**（`Pipeline → Steps → Unit` 三层执行结构），把 pipeline 拆成 `city / poi / itinerary` 三条子线：

- **city pipeline**：初始化城市维度表（city_id、name、country、经纬度）
- **poi pipeline**：Google Maps API + 高德 API 双源采集，写入 MySQL 的 `poi_test` 库
- **itinerary pipeline**：抓取行程宽表，通过 POI 匹配把行程节点关联到 poi 表

清洗侧统一了字段命名、坐标校验、city_id 强制关联；入库侧写了参数化的 Shell 导入脚本，支持按城市 / 增量重跑。最终覆盖上海、北京、广州、成都、深圳、香港、东京、里斯本等 10+ 个城市，累计 **10 万余条** POI 与行程数据。

### 2. 数据质量监控

之前团队都是"跑完 pipeline 用 SQL 手动 count"，缺质量基线。我设计了一个可复用的 **四层完整性评估脚本**：

- **第 1 层 · 行程完整性**：itinerary 的必填字段（title / dayCount / dayList）是否齐全
- **第 2 层 · POI 完整性**：poi 的坐标、city_id、name 是否为空
- **第 3 层 · 描述完整性**：poi 的 description / tips 字段填充率
- **第 4 层 · 关联完整性**：itinerary 引用的 poi 是否都能在 poi 表命中

脚本每次运行自动输出 3 份 CSV 报告：`completeness_by_city.csv`、`missing_descriptions.csv`、`poi_summary.csv`，再把这些指标接到 **FineBI 看板**上，做成实时的城市级质量监控页，包括各城市 POI 数量、描述覆盖率、匹配成功率、异常字段分布等，把质量从"事后查"变成"每日可看"。

### 3. 归因分析与问题定位

POI 匹配一开始成功率很低。我按城市把匹配失败的样本导出来，做了一轮聚类归因：

- **境内外字段差异**：境外 POI（香港、日本）返回的 `city` 字段是英文或本地语言，而我们的城市表用的是中文 name，直接字符串匹配失败
- **地址粒度差异**：高德的地址是"广州市天河区XX路"，Google 的是"XX Road, Guangzhou"，直接比对匹配不上
- **同名 POI**：不同城市有同名 POI（比如"星巴克"），仅靠名字匹配容易错配

针对这些根因我做了三件事：整理**边界案例集**（香港、日本、深圳、西安、广州五城）作为回归样本；给匹配加了**距离校验兜底**（先按名称候选，再用经纬度距离筛选，阈值内命中才算成功）；补写 AmapImportStep 里的 `city_id` 强制回填逻辑。上线后 POI 匹配准确率从大约 **30% 提升到接近 92%**，相对提升 **62%**。

### 4. 指标体系与业务洞察

之前团队对"POI 数据到底怎么样"没有统一口径。我和 mentor 一起把 POI / 行程侧的指标口径梳理成一份统一文档：

- **数据量指标**：POI 入库总数、按城市 / 国家 / 类别的分布
- **质量指标**：描述覆盖率（`有 description 的 POI 数 / 总 POI 数`）、坐标合法率、city_id 命中率
- **匹配指标**：itinerary → POI 的匹配成功率、平均匹配距离

其中"描述覆盖率"是我重点推的一个指标。之前 API 拉回来的 POI 是**完全没有** description 字段的（覆盖率 0%），下游做行程推荐时没内容可展示。我用千问补齐后，覆盖率涨到了 **51%**（剩余 49% 是没通过验证被打回的，会进入下一轮重生成）。

同时也通过对比分析定位到几个业务问题：**POI 验证通过率整体偏低**、**海外配置误采国内数据**（境外城市的 API 参数带了国内 region 前缀），把根因反馈给 mentor 后驱动了配置修复，减少了无效数据消耗。

### 5. AI 赋能数据清洗

用千问大模型（Qwen，通过阿里云 DashScope 调用）搭了一个 **"生成 → 验证 → 重生成"** 的闭环：

1. **生成环节**：把 POI 的 name / address / category / 用户评论等已有字段拼进 Prompt，让千问输出一段 80-120 字的 description 和一个更规范的 title，Prompt 里强约束"不要编造评分、营业时间等未提供的信息"
2. **验证环节**：对 LLM 输出做规则校验（长度、是否含幻觉关键词、是否重复 name），再抽样让另一个 Prompt 做"事实一致性"打分，通过阈值的进库
3. **重生成环节**：没通过验证的样本回到队列，用调整过的 Prompt 或补充上下文重跑

这套流程让 POI 描述覆盖率从 0 涨到 51%，也顺带把一批脏的 title（含乱码、地址片段）改写成了规范的短标题。

## 结果 (Result)

### 量化成果

| 指标 | 数值 | 说明 |
|------|------|------|
| 数据覆盖 | 国内外 10 万+ 条 | POI + 行程数据，10+ 城市 |

### 核心收获

1. **技术能力**：完整走了一遍数据工程的链路——多源 API 采集、Pipeline 分层、字段清洗、入库、质量评估、LLM 增强，Python + SQL + FineBI + LLM API 的组合用熟了
2. **业务理解**：从 POI 匹配失败这类"看着琐碎"的问题里学会了做归因——先聚类分类，再定位根因，再产出可复用的兜底策略，而不是逐条 case 修
3. **工程习惯**：养成了**指标先行**的意识（改动前先看基线、改动后跑同一套评估脚本对比），也开始用 Git 分支 + PR + Code Review 的规范协作方式

## 面试话术

我目前在龙腾出行 AI 研发部做数据实习生，从今年 4 月开始，主要负责公司 DataPipeline 里 **POI 和行程数据** 的采集、清洗、入库和质量监控。

**背景**是团队要为上层业务提供一个 POI + 行程的基础数据库，数据来自 Google、高德、Tavily 三家 API，字段口径不统一、描述字段基本是空的、境内外差异也大，我要做的就是把这条链路打通、把数据质量做上来。

我讲三个印象比较深的事：

**第一个是 POI 匹配准确率的优化。** 一开始 itinerary 里的 POI 匹配上高德数据源的成功率只有 30% 左右。我把失败样本按城市导出来做聚类归因，发现主要是三类原因：境外城市字段是英文、地址粒度不一样、还有同名 POI。我做了一个边界案例集（香港、日本、深圳、西安、广州五个城市）作为回归样本，加了一个**距离校验兜底**——名称候选出来之后再用经纬度距离筛选，阈值内才算命中。最后匹配准确率从 30% 拉到 92% 左右，相对提升 62%。

**第二个是数据质量监控体系。** 之前团队都是跑完 pipeline 用 SQL 手动查数据。我写了一套**四层完整性评估脚本**——行程、POI、描述、关联字段四层，每次自动出 3 份报告，再接到 **FineBI 看板**上做城市级的实时监控。这样数据质量从事后查变成每天可看，也顺带定位到了"海外配置误采国内数据"这种业务问题。

**第三个是 LLM 赋能数据清洗。** 之前 API 拉回来的 POI **完全没有 description 字段**，覆盖率是 0，下游行程推荐没内容展示。我用**千问大模型**搭了一个"生成 → 验证 → 重生成"的闭环：Prompt 里强约束不能编造评分、营业时间这些没给的信息，输出后再做规则校验和一致性打分，通过的进库、没通过的回队列重跑。最后描述覆盖率从 0 涨到了 51%。

整体上这段实习让我第一次完整参与了一个数据工程的项目链路，最大的收获是学会了**用指标驱动改动**——先看基线、再动手、再用同一套脚本对比效果，而不是拍脑袋改。
