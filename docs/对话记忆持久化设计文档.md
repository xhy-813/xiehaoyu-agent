## 1. 背景与目标

当前 `POST /api/chat` 是无状态的：Agent 只看到当次请求的 message，没有历史；前端刷新即丢。为完善作品集聊天助手体验，本期实现：

- 匿名用户身份识别（不引入登录）
- 服务端持久化对话历史（含全量 artifacts，支持完整回放）
- 智能上下文注入（早期消息摘要 + 最近 N 轮原样）
- 左侧栏切换、搜索、重命名、删除会话

**非目标**：账号体系 / 多设备同步 / 跨设备导入导出 / 会话共享分享。

## 2. 用户身份

- 前端首次访问在 `localStorage` 生成 UUID v4 存为 `user_id`
- 所有 API 请求带 `X-User-Id` header
- 后端不做鉴权，只做**归属校验**（session_id 必须属于当前 user_id，否则 403）
- 清 localStorage / 换设备 = 全新用户，历史不可恢复（i 方案）

## 4. 数据模型 `data/sessions.db`

```sql
CREATE TABLE sessions (
  id           TEXT PRIMARY KEY,     -- UUID
  user_id      TEXT NOT NULL,
  title        TEXT,                 -- LLM 自动生成或用户重命名；生成中为 NULL
  summary      TEXT,                 -- 早期消息摘要，>10 轮触发
  summary_upto INTEGER DEFAULT 0,    -- 摘要已覆盖到第几条消息（messages.id）
  created_at   TIMESTAMP NOT NULL,
  updated_at   TIMESTAMP NOT NULL
);
CREATE INDEX idx_sessions_user ON sessions(user_id, updated_at DESC);

CREATE TABLE messages (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id    TEXT NOT NULL,
  role          TEXT NOT NULL,        -- 'user' | 'assistant'
  content       TEXT NOT NULL,
  artifacts_json TEXT,                -- 该轮 tool_end 轨迹（trace 数组），见 §5 回放协议
  created_at    TIMESTAMP NOT NULL,
  FOREIGN KEY(session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
CREATE INDEX idx_messages_session ON messages(session_id, id);
```

- `artifacts_json` 复用 `agent/graph.py::_serialize_artifact()` 已产出的 JSON；**落库与回放全程保持字符串不解析**（原因见 §5 回放协议约束）
- planner_decision **不落库**（回放不需要，流式瞬时状态）
- MVP 搜索用 `LIKE '%q%'`（title + content）；性能不足再升级到 FTS5

### 存储实现选型

- 同步 `sqlite3`（标准库，零新依赖）+ `asyncio.to_thread()` 包装所有读写，避免阻塞 FastAPI 事件循环；不引入 aiosqlite（读写均为简单 KV 式操作）
- 开启 WAL：`PRAGMA journal_mode=WAL`，提升读写并发
- 单连接 + `threading.Lock` 串行化写入（SQLite 单写者）
- 启动时自动建库建表（`CREATE TABLE IF NOT EXISTS`），无需迁移脚本
- 功能二的 `datasource_store.py` 复用同一套封装与同一个 `sessions.db` 文件

## 5. 后端 API

| Method | Path                        | 说明                                        |
| ------ | --------------------------- | ------------------------------------------- |
| POST   | `/api/sessions`           | 新建，返回`{session_id}`                  |
| GET    | `/api/sessions`           | 列表（title / updated_at），按活跃时间倒序；title 为 NULL 时前端显示"新会话"  |
| GET    | `/api/sessions/{id}`      | 单会话所有消息，用于回放（响应形状见下方回放协议）  |
| PATCH  | `/api/sessions/{id}`      | 重命名`{title}`                           |
| DELETE | `/api/sessions/{id}`      | 删除会话                                    |
| GET    | `/api/sessions/search?q=` | 模糊搜索 title + content                    |
| POST   | `/api/chat` (改)          | body 新增可选`session_id`；推荐前端先建会话再提问（见下方幂等说明） |

所有接口从 `X-User-Id` 取身份；缺失/非 UUID → 400；`session_id` 不属于当前 user → 403。

### 会话创建幂等（重要）

前端 `sse.ts:134-162` 有 `MAX_RETRIES=3` 的指数退避自动重试，会整体重发同一 POST。若依赖"session_id 为空则服务端自动新建"，首次请求已建会话但响应中途失败时，重试会**再建一个新会话并重复写入 user 消息**。因此规定：

- **主流程**：前端发送前检查 `sessions.currentId`，为空则先 `POST /api/sessions` 创建并缓存，再发 chat（chat 请求始终携带 session_id）
- **兼容路径**：服务端保留"session_id 为空时隐式新建"（响应 header `X-Session-Id` 带回），仅供老版本前端/裸 curl 使用，不作推荐

### 回放协议（`GET /api/sessions/{id}` 响应形状）

```json
{
  "session": {"id": "...", "title": "...", "created_at": "...", "updated_at": "..."},
  "messages": [
    {"id": 11, "role": "user", "content": "...", "steps": null, "tools": null, "trace": null, "created_at": "..."},
    {"id": 12, "role": "assistant", "content": "...", "steps": 3,
     "tools": ["query_data", "visualize", "explain_result"],
     "trace": [
       {"tool": "query_data", "args": {"question": "..."}, "summary": "...",
        "artifact": {"sql": "...", "df_json": "<JSON 字符串>", "df_shape": {"rows": 12, "cols": 2}, "df_columns": ["..."]}}
     ],
     "created_at": "..."}
  ]
}
```

约束：

- `artifact.df_json` / `artifact.figure_json` 必须是 **JSON 字符串**——前端 `InlineResult.vue`/`ChartRenderer.vue` 内部自行 `JSON.parse`；后端若落库时解析成对象、回放返回对象，前端会静默渲染为空
- `steps` = 该轮 trace 条数；`tools` = trace 中 tool 名的有序去重列表（回放时由 artifacts_json 推导，不单独落库）
- **不要用** SSE `final_answer` 事件里的 `steps`——该值恒为 0（既有 bug，见 §15）
- 现有渲染组件零改动复用：`ChatMessage.trace` 填入上述 trace 数组即可
- 单会话不分页：全局每日 200 问限流隐含约束了单会话长度，MVP 阶段可接受

## 6. 记忆注入策略（智能摘要，方案 d）

计数单位统一为**轮**（1 轮 = 一条 user + 一条 assistant）。

进入 planner 前：

1. 读该 session 的 `summary` + 最近 `MEMORY_RECENT_TURNS=5` 轮消息
2. 拼装为**独立 user 角色上下文消息**，置于 system 之后、当前问题之前：`[会话摘要] {summary}\n\n[最近对话]\n{recent}`
   - planner system prompt（`prompts/planner.md`）保持模块级缓存不变，不做 format 注入

SSE 流结束（含用户停止/断连，见 §10）后：

1. 写入本轮 user + assistant 消息
2. 若 `总轮数 > MEMORY_SUMMARY_TRIGGER_TURNS=10` 且 `距上次摘要的新增轮数 > MEMORY_SUMMARY_MIN_NEW_TURNS=3`（新增轮数 = `summary_upto` 之后的消息条数 ÷ 2，`summary_upto` 是 messages.id 水位）：
   - `asyncio.create_task` 后台生成新 summary（不阻塞响应）
   - 摘要输入 = 旧 summary + `summary_upto` 之后到当前的全部消息；输出覆盖 `summary`，更新 `summary_upto`
   - **并发防护**：每 session 一个"摘要生成中"标记（进程内 set），进行中则跳过本次触发；任务必须 try/except 兜底并在 finally 清除标记

title 自动生成：首条 assistant 完成后异步 LLM 生成（≤20 字），失败降级为"首条用户消息前 20 字"；生成期间 title 为 NULL，前端显示"新会话"。

## 8. 清理策略（定时任务）

后端启动挂 `asyncio` 协程，每 `MEMORY_CLEANUP_INTERVAL_HOURS=6` 小时执行：

- `DELETE FROM sessions WHERE updated_at < now - MEMORY_MAX_AGE_DAYS days`
- 每 user_id 若 session 数 > `MEMORY_MAX_SESSIONS_PER_USER=50`，删最老的
- 部署为单 worker（现状），协程不会重复执行；若未来多 worker 需加锁或移到独立 cron

## 10. 错误处理与边界

- `X-User-Id` 缺失/格式错 → 400，前端重新生成 UUID 并重试一次
- `session_id` 不属于当前 user_id → 403
- **用户停止生成 / 客户端断连**：已产生的部分结果照常落库（user 消息 + assistant 已有内容 + 部分 trace），与前端 finally 兜底保留部分 trace 的现有行为一致；回放时该轮显示为不完整但不报错
- SQLite 写入失败 → 记 log，不影响 SSE 流本身（先保证用户看到回答）
- summary 生成失败 → 静默，下一轮再试
- 单条 artifacts_json > 1MB → warning log，暂不截断
- 后台任务异常必须 `try/except` 兜住，不能污染主事件循环

## 15. 关联修复（实施时顺手处理的既有问题）

- **`final_answer.steps` 恒为 0**：`finalize_node` 只返回 `{"final_answer": answer}`（`agent/graph.py:253`），updates 模式下取不到 step，事件中 steps 恒为默认值 0（`graph.py:364`）。修：`finalize_node` 返回值补上 `step`；持久化一律用 trace 长度
- **心跳死代码**：`_heartbeat()` 定义了但全文无消费点（`backend/app/routers/chat.py:35-38`），README 声称有心跳。修：在 `_event_generator` 中接入（每 15s 发 `: heartbeat` 注释行）或删除并与 README 对齐
- **断连后仍 yield `[DONE]`**：`chat.py:46` 在 `is_disconnected()` break 之后的路径上仍会执行。修：break 后直接 return，不再发 `[DONE]`
