## 一、目标：什么叫「有业务价值」

先把模糊诉求变成可检查标准。基于工业界公开实践收敛 8 条判定标准（按重要性排序），方案任务与标准的覆盖关系在第四章总表标注：

| # | 标准 | 可检查点 |
|---|------|---------|
| 1 | **口径统一**（语义层/指标中心化） | 同一指标无论怎么问都出同一数字；改一处定义全局生效 |
| 2 | **结果可信可核验** | 每个数字附带 SQL + 口径说明 + 数据来源；答不了的问题明确拒答或反问，绝不编造 |
| 3 | **有离线评测闭环** | 金标评测集 + 准确率/执行成功率北极星指标，每次改动可报 delta |
| 4 | **错误自修复与优雅降级** | 失败有带上限的自动修复；空结果/异常值有校验；失败给部分结果而非堆栈 |
| 5 | **多轮分析连续性** | 支持追问与指代消解；已确认口径、已得结论跨轮不丢失 |
| 6 | **从查数到洞察** | 能回答「为什么降了」而非只报「降了多少」（归因下钻） |
| 7 | **有可交付产出物** | 分析结果可带走：报告、导出文件，而非只停留在聊天气泡 |
| 8 | **成本与延迟工程化** | 单问成本可报数；长任务有步数/token 硬上限 |

> 说明：标准 1-4 与 8 的工业界论据（Uber QueryGPT、Pinterest Text2SQL、Snowflake Cortex Analyst 等）来自调研 agent 的知识库（调研环境网络受限未能在线核验，截至 2026-01），**面试引用前需核验 URL 与数字**；标准本身的合理性不依赖这些引用。

### 现状家底（已有的，不重复建设）

差距分析同时确认了以下已闭环能力，本方案只在缺口处施工：

- Text2SQL 四层纵深防御：sqlparse 结构校验（剥注释/字符串字面量防误杀）→ 只读 URI 连接 → progress handler 语句熔断 15s → 结果 1 万行截断；失败反馈重写 ≤3 轮（chatbi/validator.py:69-113；agent/tools/query_data.py:38、64-76、128-147、234-236）

- 会话持久化 + 触发式摘要 + 记忆注入 planner
- prompt 资产化（.md + 版本头）与三层测试体系

## 二、调研依据

### 2.1 airda（哈工大深圳 IDS，1776 star，2025-01 停更）

**一手验证**（GitHub REST API 抓取 README 全文 + 约 20 个核心源码文件）：定位「面向数据分析的多智能体」，两级架构（自研 framework 层 + DataAgent 业务层），问答链路为 Searcher（向量找表）→ SqlGenerator → Explainer（流式人话解读 SQL）三段式；核心设计是**表级知识卡片（Instruction）**：DDL + 表注释 + 列注释结构化入库，双通道加权 schema linking（表注释相似度 ×30 + 列注释相似度 ×1，阈值 65 分 + top-k 兜底）。

**关键反面发现**（README 进度表 + 源码双重证实）：其宣传的多智能体协同、任务规划、self-debug、可视化**均未实现**；已发布代码**不执行 SQL**、无结果展示、无错误修正。它的「产品感」一半来自工程结构、一半来自愿景叙事——这本身就是面试素材：「我核实过它的实现边界，并在自己项目里闭环了执行、图表与纠错」。

| 可借鉴设计 | 本方案吸收处 | 注意 |
|---|---|---|
| schema 资产化（表级知识卡片） | T1 指标注册表 + 字段语义注释 | 9 表场景不存在「千百张表找数」，叙事必须转为「字段语义/指标口径」，否则面试官一问就穿帮 |
| 双通道加权 schema linking | 暂缓（见第八章） | 9 表全量注入无检索必要 |
| Explainer 人话解读节点 | 现状已有 explain_result，T3 强化 | 我们的解读面向业务结论，比它的 SQL 逐句解释更进一步 |
| 需求确认反问（其 roadmap 第一项，未实现） | 暂缓（见第八章） | 与 planner.md「模糊则追问」规则重叠 |
| 数据源生命周期 CLI（add/sync/ls） | 暂缓（见第八章） | 换数据集需求已被 08-09 决策否决 |
| 终点是应用（大屏/API）而非 SQL | README roadmap 叙事 | 零成本，写进后续迭代话术 |

### 2.2 DeepAnalyze（人大 RUC DataLab，4488 star，arXiv:2510.16872）

**一手验证**（GitHub + arXiv 全文 + deepanalyze.py 源码）：「首个面向自主数据科学的 agentic LLM」——单一 8B 模型 + 五动作特殊 token（Analyze/Understand/Code/Execute/Answer），推理循环仅约 150 行（stop token → 正则抽代码 → exec → traceback 结构化回喂，上限 30 轮）；**产出物是分析师级研究报告**（可渲染 PDF）；服务层 thread_id 维持会话级 workspace，生成文件以 URL 返回。自主性来自 curriculum agentic training（470K SFT + 20K cold start + 15K GRPO RL）。

| 可借鉴工程模式 | 本方案吸收处 | 注意 |
|---|---|---|
| 结构化分析动作流 + 过程叙事化渲染（JupyterUI 把动作段转 notebook cell） | T5 plan 进度卡片 | 用 prompt 协议 + LangGraph 编排「翻译」其动作流 |
| 执行反馈自我纠错环 | 现状已闭环（执行层）；T2-3 补语义层校验 | 我们的 3 轮上限比它的 30 轮更适合 API 成本模型 |
| 报告一等产出物 | T6 报告模式 | 骨架模板化补偿通用模型长链条不稳定性 |
| 会话级 workspace + 产物文件化 | T7 | 其裸 exec() 不可照抄（见第八章 Python 执行暂缓理由） |
| 金标评测集方法论（DABStep-Research） | 现状已有 50 题；T2-1 分层升级 | — |

**明确不可复制**：训练流水线、8B 专训基座、30 轮长循环的成本（论文中 workflow agent 单任务 $12-39）。补偿策略：报告骨架模板化 + 步数/token 硬上限 + 每章独立校验。面试话术定位：「借鉴其动作协议与产物形态，实现**受控自主性**」，不声称复刻。

### 2.3 spring-ai-alibaba/DataAgent（2455 star，2025-09 创建，活跃维护中）

**一手验证**（GitHub REST API：README、ARCHITECTURE / KNOWLEDGE_USAGE / ADVANCED_FEATURES / QUICK_START 四份文档、17 个 prompt 模板全文、PlannerNode / PlanExecutorNode / SemanticConsistencyNode / FeasibilityAssessmentNode / Plan / ExecutionStep 等核心源码）：阿里 Spring AI Alibaba 官方生态的「企业级智能数据分析师」，Java + StateGraph（与 LangGraph 同范式）+ Nuxt 前端。与 airda 相反，**宣传的节点全部有源码实现**：意图识别 → 证据召回（业务知识 RAG）→ 查询改写 → Schema 召回 → 表关系 → 可行性评估 → 规划 → 确定性计划校验 → 可选人工审批 → 逐步执行（SQL 步骤含执行前 LLM 语义审计；Python 步骤走 Docker 任务级沙盒）→ 报告生成。

**对本案的核心价值：它是三个参考项目里唯一与本项目同形态（通用 API 模型 + 编排框架 + 提示词工程）的工业界实现**，其设计可直接对照翻译，无需像 DeepAnalyze 那样做「训练 vs 编排」的折扣换算；且其未公布任何评测集与准确率数据——本案 50+8 分层基线反而构成差异化叙事点。

| 可借鉴设计 | 本方案吸收处 | 注意 |
|---|---|---|
| 三层知识体系：语义模型（字段映射 + 同义词 + 枚举值解释）/ 业务知识（指标公式）/ 智能体知识（SOP、Q&A few-shot 救火） | **T1 补强**：注册表增加字段级语义（枚举值解释、同义词）；「字段映射不写计算逻辑、计算口径只放指标层」的分层纪律 | 其指标定义是自然语言 + RAG 召回，本案 sql_template 参数化路由的口径一致性更强，维持不变 |

## 四、阶段一任务详设（务实路线）

### T1【P0】指标语义层（2-3 天）

**问题**：差距 1。口径治理是数据分析岗的核心职业技能，项目里完全缺席等于反向证明没做过真实分析；且现有 96% 基线的成色需要口径题单独验证。

**改法**：

- **T1-1 指标注册表**：新增 `chatbi/metrics.yaml`（声明式语义模型，对标 Snowflake Cortex Analyst 的 YAML 语义层；若 pyyaml 不在依赖树则用 JSON 等价替代）。12 个核心指标，每项字段：`name` / `aliases`（中文同义词）/ `description`（业务口径）/ `sql_template`（参数化 SQL，{start_date}/{end_date}/{dim} 占位）/ `default_filters`（如 delivered 口径）/ `dimensions`（可下钻维度白名单）/ `unit`。初始指标清单：

  | 指标 | 口径要点 |
  |------|---------|
  | GMV | SUM(order_items.price)，默认 delivered 订单口径，BRL |
  | 订单量 | COUNT(DISTINCT order_id)，全状态（除非明确限定） |
  | 客单价 | GMV / 订单量 |
  | 复购率 | 购买 ≥2 次的 customer_unique_id 占全部有购买记录客户比例 |
  | 新客占比 | 当期首单客户 / 当期活跃客户 |
  | 平均评分 | AVG(review_score) |
  | 差评率 | review_score ≤ 2 的评价占比 |
  | 准时交付率 | delivered_customer_date ≤ estimated 的订单占比（delivered 口径） |
  | 平均交付时长 | julianday(delivered) − julianday(purchase) 均值，天 |
  | 运费占比 | SUM(freight_value) / SUM(price) |
  | 平均分期数 | AVG(payment_installments)，credit_card 口径 |
  | 品类集中度 CR5 | top5 品类 GMV / 总 GMV |

  同时把 text2sql.md 中的**口径语义**（消费金额按 price 而非 payment_value、客户数按 customer_unique_id、COUNT DISTINCT 语义）迁入注册表——口径的单一事实源是注册表，text2sql.md 只保留 SQL 写法规则（strftime、JOIN 类型、长表宽表等）。两个文件各司其职，消除口径双写漂移风险。

  注册表同时承载**字段级语义注释**（吸收 DataAgent 语义模型层实践，其知识文档将同义词与枚举值解释列为最高 ROI 配置）：为枚举字段写取值解释（`order_status` 各取值的业务含义及其与 GMV delivered 口径的包含关系、`payment_type` 各取值），为易混字段写业务名称与同义词（如 `price` = 商品售价 ≠ `payment_value` 实付金额）。分层纪律：字段映射与枚举解释放注册表字段层，计算口径只放指标层，互不越界。

- **T1-2 prompt 注入**：`agent/tools/query_data.py` 的 `_build_prompt`（现 :89-97）将渲染后的指标定义与 schema 并列注入；text2sql.md 升版（v1.6.0），新增【业务指标】段。
- **T1-3 指标路由**（对标 Uber 意图分类 + Snowflake verified queries）：query_data 前置路由——问题命中注册表（别名精确匹配 + embedding 相似度双档，复用现有智谱 embedding）走参数化模板 SQL（口径 100% 正确、天然附带口径说明），未命中走自由 Text2SQL 兜底；路由决策与命中指标名写入 trace，前端可展示「命中指标：复购率（模板 SQL）」。
- **T1-4 口径评测题**：eval_text2sql.py 新增 8 道「只给指标名不给口径」的题（如「复购率是多少」「客单价最高的三个品类」），与 few-shot 零重叠（沿用 808 H3 纪律），口径命中率单独报告。**同步修正基线叙事**：原 96% 基线题干内嵌口径，README 与简历表述改为分层口径（见 T2-1）。

**验收**：8 道口径题命中 ≥7；原 50 题基线不回退（波动 >2% 需说明）；同一指标两种问法（「复购率」「购买 2 次以上的客户占比」）产出同一数字；`metrics.yaml` 改一处定义后两处问法结果同步变化（现场可演示）。

**叙事点**：「改一处定义、全局口径生效」30 秒可演示；口径治理 = 数据分析岗最直接的岗位信号。

### T2【P0】可信闭环升级（1-1.5 天）

**问题**：差距 1 的评测侧 + 标准 2/3/4。demo 只演示 happy path，产品展示错误处理。

**改法**：

- **T2-2 答案自带口径**：planner.md finalize 要求新增一条——凡涉及注册表指标的回答，末尾附一行口径说明（如「口径：GMV = 已交付订单商品售价之和，单位 BRL」）；explain.md 同步（与 T3-1 的追问建议改动合并，升版一次 v1.3.0）。
- **T2-3 语义级结果校验**（现有执行错误重试之外的增量）：query_data 执行成功后增加两道轻量校验——空结果（→ 反馈「检查过滤条件是否过严」自动重试 1 次，仍空则如实说明而非硬编）；数量级异常（结果数明显超物理上限，如订单数 > 99441，→ 反馈重试 1 次）。失败路径全部落入现有 trace 机制。同时将 DataAgent 语义审计清单中两条高频坑写入 text2sql.md v1.6.0 规则层（零运行时成本）：DATETIME 范围过滤用半开区间（`>= '2018-01-01' AND < '2019-01-01'`），避免 `BETWEEN ... AND '2018-12-31'` 丢失结束日当日数据；多对多 JOIN 后聚合前先检查扇出（如 orders × order_items 后直接 SUM 订单级字段会重复计数）。不新增 LLM 语义审计节点（决策见第八章）。

**验收**：分层报告可一键生成；含注册表指标的回答 100% 带口径行；空结果场景（如「2025 年订单量」）不再硬编解读。

**叙事点**：评测驱动迭代（Pinterest 故事）；「非 happy path 处理」是 demo 与产品的分水岭。

**验收**：每条 explain 输出 2-3 条具体追问且前端可点击发问；裸查询回答必带解读；快捷问题全部场景化。

## 五、阶段二任务详设（形态路线）

### T5【P1】多步分析工作流（2-3 天）

**问题**：差距 2。这是「会写 SQL 的聊天框」与「会做分析的 Agent」的分水岭。

**改法**（planner 双模，向后兼容，不冲击现有基线）：

- 简单问题走现有单步协议不变；复杂问题（归因/对比/「分析一下」类，planner 判定）先输出**分析计划**（JSON 步骤数组，如「确认 GMV 月度趋势 → 按品类下钻 10 月后增量 → 按州下钻 → 综合归因」），存入 AgentState 新增的 `plan` / `plan_step` 字段；逐步骤执行（每步复用现有工具链），每步结果压缩进 planner 上下文，最后 finalize 综合归因结论。计划结构采用 DataAgent Plan 的成熟设计（其 NL2SQL 单步退化模式与本案「简单问题单步」同构）：`thought_process` 必须列出已检查的表/字段（可审计）；每步 `instruction` 满足**指令契约**——真实表名字段、过滤条件、期望输出列、前序步骤依赖的具体列名，禁止「查询数据」式模糊指令；最后一步必须是 finalize/结论步。
- **确定性计划校验**（非 LLM，吸收 DataAgent PlanExecutorNode 模式）：plan 进入执行前做结构校验（JSON 合法、工具名在白名单内、逐步参数非空、步数未超上限），校验失败将错误信息作为 `plan_validation_error` 注入 planner 重新规划，修复计数 ≤2 次仍失败则如实降级回答；校验全部通过才进入执行。
- plan 模式步数上限独立于 MAX_AGENT_STEPS（如总 12 步），防止 token 膨胀；router 相应扩展。
- SSE 追加新事件类型 `plan_created` / `plan_step_end`（纯追加，旧事件不变，向后兼容）；前端把 plan 渲染为进度卡片流（对标 DeepAnalyze JupyterUI 把动作段转 notebook cell 的做法），中间过程可折叠。
- planner.md 升版，新增【分析计划】段与计划示例（few-shot 1-2 条）。

**验收**：「2018 年 GMV 为什么 10 月之后增长失速」自动拆解 ≥3 步并输出带数据支撑的归因结论；现有 50+8 题基线不回退；单步问题不产生 plan 开销。

**叙事点**：能讲清「训练进模型的自主性（DeepAnalyze）vs 编排出来的受控自主性（本项目）」这一层认知，以及为什么后者是用通用 API 模型的现实最优解。

### T6【P2】报告模式（3-4 天）

**问题**：差距 3（产出物）。对标 DeepAnalyze 的核心产品形态，以 workflow 方式受控复现。

**改法**：

- 触发：用户指令（「生成 Olist 经营分析报告」）或前端入口按钮。
- **骨架模板化**：固定报告骨架——研究背景 → 数据与方法 → 主题章节（销售趋势 / 品类结构 / 地域分布 / 物流时效 / 客户评价，4-6 章）→ 结论与建议；每章 = 1-2 次 query_data + visualize + explain，复用 T5 计划机制编排，最后合成完整 Markdown 报告。
- **报告事实纪律**（吸收 DataAgent report-generator prompt）：报告 prompt 内置事实四级区分——查询事实（结果直接返回的值）/ 派生指标（由结果明确计算，须说明口径）/ 假设（数据无法证明，仅用户明确要求时标注）/ 建议（须由已确认事实支撑）；空结果规则——计数 0 是已知事实不得写「无法计算」、null 如实说明不擅自替换为 0、不推测原因；禁令——未做专门数据质量查询不得声称「无缺失/无异常/数据可信」，执行无报错或聚合有结果不能证明这些结论。
- **成本护栏**（DeepAnalyze 论文中 workflow agent 单任务 $12-39 的教训）：章节 ≤6、报告全程总步数 ≤20、token 预算硬上限、每章独立校验失败可跳过降级；SSE 长任务心跳沿用现有 15s 机制。
- 导出：报告 Markdown 复制/下载；PDF 导出列为可选增强（前端打印样式或 pandoc，不阻塞主链路）。

**验收**：一键生成 ≥4 章节报告，每章含图、含数、含结论；单次报告 token 消耗可报数（llm_tokens 日志已有埋点）；导出的 Markdown 结构完整可直读。

**叙事点**：「报告骨架模板化 vs 模型自由生成」的质量控制取舍；从问答工具到 AI 数据分析师的形态升维。

### T7【P2】workspace 产物落盘（1.5-2 天）

**问题**：差距 3（产物留存）。对标 DeepAnalyze 的 thread_id workspace + 文件服务设计。

**改法**：

- 每会话一个 workspace 目录（`data/workspaces/{session_id}/`）：查询结果 CSV、图表（Plotly HTML 自包含文件）、报告 md 落盘；新增 `GET /api/files/{session_id}/{filename}` 下载端点（文件名校验防路径穿越，session 归属校验）。
- 前端：消息内下载链接 + 会话产物列表（侧栏或折叠区）。
- 生命周期：跟随现有会话过期清理（MEMORY_MAX_AGE_DAYS=30）联动删除；写操作纳入会话写端点限流。

**验收**：查询/图表/报告三类产物可下载；过期会话产物被清理；路径穿越用例（`../`）被拦截并有测试。

**叙事点**：从 demo 到「类生产系统」的工程意识（状态管理、产物生命周期），普通 ChatBI 项目普遍缺失的一层。

### T8【P2】可视化业务感知（0.5-1 天；可提前插入阶段一末尾）

**问题**：差距 7。

**改法**：question 参与选图决策——占比类（占比/分布）→ 环形或百分比堆积；对比类（vs/对比）→ 分组柱状；漏斗类 → 漏斗图；趋势图加均值参考线；异常点简单标注（偏离均值 2σ）。`reason` 字段业务化（「占比类问题 → 环形图」而非「1x1 numeric」），前端执行轨迹可读性同步受益。

**验收**：占比/对比/趋势三类问题各出对应图型；现有表格/指标卡兜底不回退。

**叙事点**：图表为结论服务；小投入撬动面试官的直观观感。

## 九、风险与对策

| 风险 | 对策 |
|------|------|
| 指标路由误判（该走模板的问题走了自由 SQL，或反之） | 双档匹配（别名精确 + embedding 相似度阈值），低置信一律兜底自由 Text2SQL；路由决策写 trace 可审计；口径题回归覆盖 |
| 多步工作流/报告模式 token 成本膨胀 | 步数/章节/token 三重硬上限；planner 上下文沿用 800 字摘要截断；llm_tokens 日志观测单次报告成本 |
| DeepSeek 通用模型长链条不稳定（DeepAnalyze 用专训 8B 才有长链自主性） | 报告骨架模板化（模型只填槽不规划结构）；每章独立校验可跳过降级；T5 计划步骤上限 12 步；计划确定性校验 + 校验错误回炉（≤2 次，DataAgent 模式）拦截结构层不稳定 |
| SSE 协议扩展破坏前端 | 新事件类型纯追加（plan_created/plan_step_end），旧事件与字段不变；前端对未知事件类型忽略兜底 |
| 注册表口径与 text2sql.md 条文双写漂移 | 口径语义只存注册表（单一事实源），text2sql.md 只留 SQL 写法规则；808 式审查时专项检查 |
